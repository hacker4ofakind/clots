## 1. What stage 4a delivers

A web app becomes the only way to use Clots. It replaces Discord entirely: chat
with each Clot, every ask and choice, the list of what is waiting, worker
progress, commands, settings, creating Clots, connecting services, and push
notifications on the user's iPhone from a home-screen install.

Desktop has every feature, setup and configuration included. The phone is for
using Clots once they are set up: the list of Clots, chatting, and answering
what is waiting. Both work from the first release.

Claritee widgets and Clapboards come in stage 4b. Until then, Clot messages
render as markdown.

Not in this stage, though the canvas shows them for reference: the daily todo,
voice calls, browser use, computer use and Secret Storage. Their buttons,
toggles, rail items and settings pages are absent from the build, not disabled.
The browser and its live view become stage 5.

## 2. Where stage 4a sits in the parent design

It replaces the chat adapter (section 2, Components: "Chat adapter"), the
Discord layout (section 6), and the channel side of asks and choices (section
7). The sessions, the queue, the lock, the axes, the gates and every source stay
as they are. Onboarding (section 11) is built here, in the New Clot flow.

What changes in the parent design's behaviour, apart from where things are
shown:

- **Every ask has a deadline** (section 7, Asks). One setting,
  `askTimeoutMinutes` (renamed from `choiceTimeoutMinutes`, default 10),
  applies to every kind. A choice whose deadline passes goes with the Clot's
  pick, as now. Every other ask is **blocked** when its deadline passes: the
  rule is not applied, the email is not sent, the merge is not made, the memory
  question is answered no. Silence still never approves. `sendReview.days` is
  removed; an email ask blocks after the same timeout. The existing
  withdrawals (an email ask withdrawn after its review window, a merge ask
  withdrawn on a new commit, a rule ask never withdrawn) keep their other
  triggers: a merge ask is still withdrawn when the pull request changes.
- **Asks are answered with buttons**, not exact replies. The exact-reply
  matching (`yes`, `sure`, `1`, `your pick`…) is removed. A message the user
  types in a Clot's chat while one of its asks is open is handled as today's
  "any other reply" for that ask kind (feedback to the main session).
- **Commands start with `/`**, not `&`. The set is unchanged.
- **Rollover keeps one chat per Clot.** A rollover adds a note to the same
  chat; the old messages stay visible to the user and are no longer in the
  Clot's context. There are no session channels, read-only channels or
  channel pruning.
- **`clots-waiting` becomes the Waiting for you page**, built from the open
  asks and choices.

When 4a is built, the parent design's sections 2, 6, 7 and 11 are edited in
place to describe this (no change notes), and the stage list in section 16
reads: 4a web UI, 4b Claritee and Clapboards, 5 browser and live view.

## 3. Processes, network and access

```
iPhone / desktop browser
   │  https://<machine>.<tailnet>.ts.net:8443   (tailscale serve, tailnet only)
   ▼
Next.js app (web/)  127.0.0.1:3000
   │  HTTP + SSE, shared secret header
   ▼
Daemon UI API       127.0.0.1:8788
Daemon intake       127.0.0.1:8787  ◄── Tailscale Funnel :443 (webhooks only)
```

- **Repository**: npm workspaces. The daemon stays at the root; the Next.js app
  is the workspace `web/`; 4b adds `packages/claritee/`. Dependencies are added
  with `npm install -w <workspace> <name>`; the lockfile is regenerated by npm,
  never edited.
- **The daemon's UI API** listens on `127.0.0.1:8788`, a port of its own. The
  intake port 8787 stays webhook-only, because Funnel makes it public.
- **The web app** runs `next start` on `127.0.0.1:3000` as its own systemd
  service on the Pi (`clots-web.service`, started after `clots.service`). On
  the PC, `npm run web` starts it in development.
- **Tailnet-only access**: `tailscale serve --bg --https=8443 http://127.0.0.1:3000`.
  Funnel stays on 443 for the webhooks and nothing else.
- **Who may use it**: Next.js middleware requires the `Tailscale-User-Login`
  header that `tailscale serve` adds, and compares it with `ui.owner` in
  `clots.config.json`. Any other value, or none, gets a 403 page. A request
  that reaches port 3000 directly (no header) is refused the same way.
- **The browser never calls the daemon.** Next.js route handlers and server
  components call the UI API with the header `X-Clots-UI-Secret`, the value of
  `CLOTS_UI_SECRET` in `.env` (created on first start). The API refuses a
  request without it, so no other local process can drive the daemon.
- **The deploy script** (`scripts/deploy.mjs`) builds the web app, installs
  `clots-web.service`, and sets up `tailscale serve` on the Pi; it no longer
  creates a Discord bot or server.

## 4. The daemon's UI API

JSON over HTTP, all under `/api/v1`, plus one event stream. The web app wraps
each call in a typed client (`web/lib/daemon.ts`) shared by server components,
route handlers and the stream proxy. The API's request and response shapes are
zod schemas in `src/ui-api/schemas.ts`, imported by both sides.

| Area | Endpoints |
|---|---|
| Clots | list (name, icon, order, state, unread, waiting count); one Clot's info (repository, connections); reorder; create (section 9); edit; delete |
| Messages | page through a Clot's chat (newest first, cursor); send a message (text and attached images); the slash command list |
| Asks | list open asks and choices; answer one (`allow`, `block`, `edit` with new text, `pick` with an option) |
| Workers | the workers of a turn, with status and pull request |
| Settings | read and write General settings; UI preferences |
| Keys | list `.env` key names with their last 4 characters; set one; remove one |
| Integrations | inboxes and Composio accounts (list, add, edit, remove); search Composio toolkits; start the configurer; connection status |
| Push | register and remove a push subscription; the VAPID public key |
| Stream | `GET /api/v1/stream` (Server-Sent Events) |

**The stream** sends one event per change, each with an increasing `id`:
`message.created`, `message.delta` (streamed text), `message.done`,
`activity` (a tool-activity line), `clot.state` (idle, working, paused,
failed, with a reason), `ask.opened`, `ask.updated` (timer state),
`ask.closed` (with its outcome), `workers.updated`, `config.changed`,
`clot.build` (New Clot progress), `integration.status`. The daemon keeps the
last 1,000 events in memory; a client that reconnects with `Last-Event-ID`
gets what it missed, or a `resync` event telling it to refetch. A heartbeat
comment goes every 20 seconds. The web app proxies the stream through a route
handler that adds the secret.

**Streaming text**: the session manager runs main-session turns with the Agent
SDK's partial messages on, and forwards text deltas as `message.delta`. The
stored message is the final text.

## 5. The conversation store (replacing the chat adapter)

The `ChatAdapter` interface, `src/chat/discord.ts`, `room.ts`, `names.ts` and
`discord.js` are removed. Everything that posted to a channel now writes to the
conversation store, a set of SQLite tables, and emits a stream event.

- `messages`: one row per item in a Clot's chat, with `kind`: `user`,
  `clot` (the main session's text), `activity` (the turn summary and
  tool-activity lines), `note` (rollover, context limit, ask outcomes, daemon
  notices such as a global memory applied), `ask` (points at the ask), and
  `workers` (points at a turn's workers). Each row has its session ID, so the
  UI can mark where a rollover happened.
- The recap that starts a new session is a `note` with the recap text, folded
  by default.
- **Typing** becomes `clot.state` working/idle.
- **Turn summary** (parent section 6) becomes one `activity` message after the
  turn: files changed with lines added and removed, commands run.
- **Tool activity lines**: each tool call in a main-session turn becomes a
  short line with an icon (`Searched the code for …`, `Read issue #31`,
  `Asking to send an email`), built from the tool name and its input by
  `src/conversation/activity-lines.ts`. Workers' tool calls are not shown.
- **Mentions and pings** are gone; push notifications (section 8) take their
  place.
- **Global memory posts**, standing rule notices, recipe notices and every other
  daemon post become `note` messages in the right Clot's chat.
- Old Discord history is not imported.

## 6. Asks and choices

The asks component keeps its kinds, handlers, axes and closing-exactly-once
rule. What changes is how an ask is shown and answered.

- **Opening**: an ask becomes an `ask` message in its Clot's chat and an entry
  in Waiting for you. Its deadline is `opened + askTimeoutMinutes`.
- **Answering**: the API's answer call closes it with the outcome. The email
  kind also takes `edit`: the new body replaces the draft before sending, and
  the main session gets a note listing what the user changed. An answer to an
  ask that already closed returns its outcome, which the UI shows as a toast.
- **Feedback**: a message sent in the Clot's chat while its ask is open is
  treated as that kind's "any other reply" (parent section 7), exactly as now.
- **Deadline**: a timer in the gate ticker closes asks whose deadline passed: a
  choice goes with the Clot's pick through the existing timeout turn; every
  other ask closes as blocked. After a restart, passed deadlines close at once.
- **Timer states**, shown on each ask: calm above 5 minutes, calling from 5 to 1
  minutes, urgent under 1 minute. "Urgent" in the Waiting for you summary
  counts asks under 1 minute.
- **Limits** (`maxProposals`, labelled "Open rule asks per Clot") are unchanged.
- **Withdrawal** still closes an ask when what it acts on changes; the UI shows
  the outcome as a note.

## 7. Screens

The canvas is the visual reference for each screen; the design system's
components and README are the rules. This section lists behaviour the mockups
cannot show.

### Shell (desktop)

- The rail, the page container and the optional side pane, as in the design
  system's Layout section. Side pane width is dragged on its grip, saved per
  Clot in UI preferences; dragging to the left edge makes it full width,
  dragging to the right edge closes it. No close or full-screen buttons.
- Rail order is the Clots' order, changed by dragging in the rail (persisted
  through the reorder endpoint). With more than three Clots, the rest and New
  Clot collapse into a "…" menu.
- The bell shows a `highlight` dot while anything is waiting.

### Waiting for you

- Asks grouped under each Clot's heading, Clots in rail order, asks oldest
  first. The summary reads "N waiting · M urgent".
- Merge and rule asks: Decline, Open in chat, Approve. Email asks: Edit, Don't
  send, Open in chat, Send, with the body in a hover preview on the subject.
  Choices: the two options as buttons with the Clot's pick marked, then Open in
  chat.
- Empty state: the coffee icon, "Continue with your life!", "None of your Clots
  are waiting for you."
- Open in chat and Edit go to the Clot's chat and scroll to the ask card.

### A Clot's chat

- Header: the Clot's name, centred. Right side: Info (opens the info pane) and
  Clapboards (4b; hidden until the Clot has one).
- Messages, activity lines, notes, ask cards and worker cards in order. Your
  messages are right-aligned `muted` bubbles; the Clot's are plain text, in
  markdown (`react-markdown` with `remark-gfm`; raw HTML is not rendered;
  links open in a new tab). Timestamps show under a group of messages from the
  same side within 5 minutes.
- The info pane: repository, connections (each with the service's real logo
  from Composio, or Phosphor's for email), and nothing else in this stage.
- Composer: attach (desktop), text, send. Pasting an image attaches it on both
  desktop and phone. Enter sends, Shift+Enter adds a line. Images go to the
  Clot as image content in the prompt.
- Slash menu on `/`: every command with its options and description in plain
  English, fuzzy filtered, matched prefix in bold. On a phone it is narrower and
  has no descriptions.
- Scrolling up loads older messages, across rollovers.

### Worker card

One card after the turn that started workers: each worker's brief, model and
effort; the first two shown and "N more"; a footer with the group's status
("4 workers running" in `highlight-ink`, then "4 pull requests opened").
Each row links to its pull request once there is one.

### Settings

- **General**: time zone, theme (system, light, dark), content width (wide,
  medium, narrow; default wide), start a new session at (`rolloverPercent`),
  workers at once (`maxWorkers`), open rule asks per Clot (`maxProposals`),
  ask timeout (`askTimeoutMinutes`, as the time input), public URL. Save writes
  and applies (section 10). Theme and content width are UI preferences, saved
  at once.
- **Manage Clots**: each Clot with its icon, name, repository, state (working,
  idle, paused with reason), Edit (opens the New Clot steps prefilled) and
  Delete. Delete is refused for the home Clot; for others it asks for the name
  typed in, then stops the container, removes the config entry and keeps the
  volumes and the chat history (a later Clot with the same name gets them
  back). Order is changed in the rail.
- **Integrations**: Inboxes (email accounts: list, add, edit, remove), Composio
  (accounts: list with scope and audience, add, edit, remove) and Keys (the
  `.env` keys: name, last 4 characters, replace, remove, add). Secret Storage
  is absent.

### Phone

- Routes: Clots, a Clot's chat, Waiting for you. The floating tab bar shows
  Clots and Waiting, hides in a chat and while the keyboard is open, and stays
  inside the safe areas.
- The chat has a back button and edge-swipe back, no header actions, no attach
  button.
- Asks on Waiting for you show only Block and Allow (or the choice options);
  tapping the row opens it in the chat.
- A one-time "Get a notification when a Clot needs you" row with Turn on, in
  `highlight-soft`, until notifications are allowed or dismissed.
- Settings, New Clot and integrations are not reachable from the phone.

## 8. Push notifications and the installed app

- **Install**: a web app manifest (name Clots, the mark as icon in all sizes,
  `display: standalone`, theme colours from `background`), and a service
  worker that only handles `push` and `notificationclick`. No offline
  caching.
- **Keys**: VAPID keys created on first start and saved to `.env`
  (`VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`); the `web-push` package sends.
- **Subscriptions** in SQLite, one per device; a send that gets 404 or 410
  deletes it.
- **What is sent**: a new ask or choice (title: the Clot's name; body: the ask's
  one-line summary); an ask entering its last minute; a choice the timeout
  decided; a Clot paused or failed; a Clot's reply while no device has been
  visible and in use in the last 2 minutes (a desktop tab left open at home
  does not count). Tapping opens the ask in its chat, or the chat.
- On iOS, permission is asked only from the Turn on button, in the installed
  app.

## 9. Creating a Clot

1. **Icon, name, repository.** The icon picker offers every Phosphor icon
   (regular weight, searchable, eight colours) or an upload (SVG, PNG, JPG,
   WebP, ICO, or pasted). The daemon checks the name is free and a valid
   container name, and that `clots-dot-dev` can reach the repository; if an
   invitation is pending it accepts it with its own token, and if there is
   none the step shows how to invite `clots-dot-dev` with Check again.
   Uploaded icons are stored under `data/icons/`, with an active variant made
   with `sharp`: two colours are swapped, anything else is inverted. After
   Next, the heading animates into the icon and "Creating <name>".
2. **Tools.** Shared Composio accounts are listed first; Add a tool opens the
   integration dialog (section 11), scoped to this Clot. A right-click menu on
   a tool offers Edit settings, Reconnect, and Remove from <name>.
3. **Create <name>.** The daemon writes the config entry, clones the
   repository and builds the container, sending `clot.build` progress (cloning,
   building, starting). A failure shows its log with Retry. When the container
   runs, the user lands in the new Clot's chat.

The Clot's first message is the onboarding checklist (parent section 11), with
each item checked by a real test: the GitHub webhook (the address and secret to
paste, checked when GitHub's ping arrives), each tool's connection, and a branch
pushed with the Clot's token. Checklist state is saved, so onboarding resumes.

Steps slide: the current one leaves to the left, the next enters from the right.
Reset clears the steps. Edit on an existing Clot opens the same steps,
prefilled, with Save instead of Create. A Clot's name cannot be changed after
creation; changing its repository re-clones into a fresh workspace.

## 10. Configuration and hot reload

- **One config store** (`src/config-store.ts`) owns `clots.config.json` and
  `.env`. It validates with the existing zod schema, writes atomically (a temp
  file, then rename) and keeps the previous file as a backup.
- **Watching**: the store watches both files (debounced 300 ms). A change made
  by hand is validated and applied like one from the UI; an invalid file is
  ignored, the last good config stays in force, and the UI shows the error in
  a toast and on the Settings page.
- **Applying**: each subsystem registers the keys it owns and a function that
  applies a change live. Time zone, hold, rollover, workers, proposals, ask
  timeout, gates, sweep, spend, Composio accounts (the existing sync), email
  accounts (reconnect the changed ones), MCP servers and recipes' secrets apply
  at once; adding or removing a Clot starts or stops its container. The intake
  port, the image and `ui.owner` apply after a restart, and the UI says so.
- **`set_config`** (the Clot tool) always becomes a config ask: the user's yes
  saves and applies it at once, with no `daemon_restart`. Because changes now
  apply live, no key is changed by a Clot without a yes; `ui` joins the keys a
  Clot can never change.
- **Keys** are written to `.env` by name; the API never returns a value, only
  the last 4 characters. A key name is generated for new integrations
  (`<TOOLKIT>_<ACCOUNT>_KEY`).
- **UI preferences** (theme, content width, side pane widths, notifications
  dismissed) are stored in SQLite, so they follow the user across devices.
- `discord` is removed from the config; `ui: { "owner": "<tailscale login>" }`
  is added.

## 11. Connecting services

**Composio tools** (the dialog on the canvas):

1. **Pick**: Composio's toolkits in a two-column grid, searchable; the list is
   cached by the daemon for a day and shows skeletons while it loads. Added
   ones show "added" with a remove button.
2. **Options**: audience (private, team, public, with their icons), whether it
   is the user's own account, shared with every Clot or only this one, events
   on or off, and a polling time (the time input; used only when the toolkit
   has no webhook trigger). Finish.
3. **Configurer**: a throwaway session (Sonnet 5.5, medium effort) runs in the
   daemon with the integration skill and these tools: read the toolkit's
   metadata and auth schemes, list its trigger types with their config
   schemas, web search and fetch, and `save_integration(entry, instructions?)`.
   `save_integration` validates the entry against the config schema and refuses
   anything else. The session picks the triggers and their config, writes a
   Composio recipe when one is needed (2e any-toolkit design), and, for an API
   key, writes step-by-step instructions that fit the dialog. The dialog shows
   skeletons while it works.
4. **Connect**: the daemon writes the entry and reloads. For OAuth, it gets the
   sign-in link from Composio (never from the configurer), shows it as a
   button that opens a new tab, and watches the connection until it is active;
   Done stays disabled for 5 seconds. For an API key, the field and the
   configurer's instructions; the key goes straight to `.env` and never reaches
   the configurer. Done is disabled while the field is empty. Steps 3 and 4
   have no close button, so a stray click cannot cancel a half-made
   connection; Back returns to options.

**Inboxes**: a form with the address, the provider (detected from the domain,
which also picks the icon), the password or app password (saved to `.env`),
the folders or labels to watch, and shared or one Clot.

## 12. Error handling

- **Daemon unreachable**: a banner over the page ("Can't reach the Clots
  daemon. Retrying…") and reconnects with backoff; actions are disabled until
  it is back.
- **Stream gap**: `resync` makes the UI refetch the open screen.
- **Sending fails**: the message stays in the chat with Retry.
- **Answering a closed ask**: a toast with how it ended.
- **Invalid settings**: the error next to the field; nothing is saved.
- **Container build fails**: the log and Retry (section 9).
- **Configurer fails or produces an invalid entry**: the dialog says so and
  offers to try again or go back; nothing is written.
- **OAuth never completes**: the dialog keeps waiting; Back returns to options;
  an abandoned connection is removed from Composio after an hour.
- **Push send fails**: logged; a dead subscription is deleted.

## 13. Building it

- Next.js (App Router), React, TypeScript, Tailwind CSS v4, shadcn/ui
  components added with the shadcn CLI and restyled to the design system,
  `@phosphor-icons/react`, `motion`, `next/image`, `next-themes`.
- Tokens: the design system's `tokens.json` becomes `web/app/globals.css`
  (`:root` and `.dark`, mapped in `@theme inline`). Component styling uses
  the tokens; no literal colours.
- **Mockup to code**: the canvas is plain HTML for looking at. Never copy its
  markup, its pasted icon masks, its classes or repeated utility strings. Every
  input, button, select, switch, checkbox, dialog, menu and tooltip is the
  shadcn component; icons come from Phosphor's package; images use
  `next/image`; repeated structures become components.
- Custom components (no shadcn equivalent): the time input, ask actions, timer,
  ask card, worker card, composer, rail, side pane, ClapboardLink (4b), the
  Clapboard icon, the logo.
- The design system's README rules apply to all UI copy (no em dashes, the
  Clot's name alone, verbs on buttons).

## 14. Testing

- **Unit (vitest)**: the UI API's handlers and schemas; the conversation store;
  activity lines; ask deadlines (each kind blocked, a choice taking the pick,
  restart with passed deadlines); answering with edit; feedback during an open
  ask; config store (atomic write, backup, invalid file ignored, each
  subsystem's apply); keys never returned; Tailscale identity and secret
  checks; push subscription pruning.
- **End to end (Playwright)** against the daemon with a fake session runner:
  sending and streaming a reply, answering each ask kind from the chat and from
  Waiting for you, the slash menu, New Clot (with a fake Docker), adding a
  Composio tool with a fake Composio, settings save and reload, reconnecting
  the stream. Each at desktop and phone sizes, in both themes, with axe
  accessibility checks.
- **Live checks** (run by me where they need no user hands): the web app on
  the Pi behind `tailscale serve`, a real Clot conversation, each ask kind,
  adding a Composio toolkit with OAuth and one with an API key, a hand edit to
  `clots.config.json` picked up live. The user installs the app on the iPhone,
  turns on notifications, and confirms a notification arrives and opens the
  ask.

## 15. Done when

- Discord is gone from the code, the config and the deploy.
- On the iPhone's home-screen app and on desktop, the user can chat with each
  Clot, answer every kind of ask, and see what is waiting; asks block at their
  deadline and choices take the Clot's pick.
- A new Clot can be created and onboarded entirely from the UI.
- A Composio toolkit can be connected with OAuth and with an API key from the
  UI, and an inbox added.
- Settings and hand edits to the config apply without a restart, except the
  keys marked as needing one.
- Push notifications arrive for asks and open them.
- Every screen matches the canvas and follows the design system, in both
  themes, at phone and desktop widths.

## 16. Risks

- iOS web push needs the app installed to the home screen and has been
  unreliable after iOS updates; notifications are the only way the user hears
  from a Clot while away.
- The UI is reachable only on the tailnet: the phone needs Tailscale connected.
- Removing exact-reply matching means an ask can only be answered in the UI;
  if the web app is down, asks block at their deadline.
- A 10-minute default for every ask is short for emails the user wants to
  think about; the setting is global.
- Next.js adds about 150 MB of memory on the Pi.
